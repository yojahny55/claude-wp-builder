# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Claude Code plugin**, not an application. Almost everything here is markdown that instructs
Claude at runtime — commands, agents and skills. There is no build step and no runtime for the
plugin itself; the root `package.json` is dev tooling only. The executable code it ships is
`bin/*.sh` and `bin/*.mjs` (several are load-bearing gates: `wp-config.mjs` is the single
definition of a valid `.wp-create.json`, `decision-sheet.mjs` parses `design_impact` approvals),
`bin/lib/`, the PHP under `skills/*/scripts/`, `plugins/store-kit/`, `starter-theme/**` and
`templates/agentic/agentic.php`. What each tool does: `docs/plugin-code.md`.

Editing a "feature" therefore usually means editing prose contracts, and the tests assert on
those contracts (grep for required tokens in the markdown), not on program behavior.

## Testing

Each check is a standalone bash script that prints `PASS` or exits non-zero. No framework.

```bash
bash tests/checks/wp-yolo-gate.sh        # one check
bash tests/run.sh -j 8                   # all checks in parallel; --exclude "a.sh b.sh" skips some
```

`tests/run.sh` runs every check and then reports, counting `SKIP` separately from `PASS`.
Browser checks need a `playwright-core`: point `PLAYWRIGHT_CORE` at one already on the machine
(for example `$(npm root -g)/@playwright/test/node_modules/playwright-core`) rather than
installing one. Checks that need a real WordPress skip unless `WP_FIXTURE=1` or `PLL_TEST_SITE`
is set.

CI also runs `node --check` on `bin/*.mjs`, `bash -n` and `shellcheck`, `bin/doc-sync-check.sh`
and `php -l`. **The PHP lint is pinned to 7.4** (8.0 for `starter-theme/__cinematic__/`): those
scripts run inside the client's WordPress, and `php -l` on 8.x accepts syntax that is fatal on
7.4. Run the checks yourself before claiming a change works.

Detail (the WordPress fixture and its `net-guard`, the CF7 delivery check, visual baselines, what
no check covers): `docs/testing.md`.

## Architecture

Four layers, strictly ordered:

```
commands/*.md   user-facing slash commands — orchestration, argument parsing, step-by-step flow
   ↓ dispatches
agents/*.md     specialized subagents (wp-template, wp-css, wp-acf, wp-audit-*, wp-normalize…)
   ↓ reads
skills/*/SKILL.md   knowledge libraries — methodology, never actions. user-invocable: false
   ↓ produces
starter-theme/ + templates/   PHP theme scaffolds and env/plugin-profile configs copied per project
```

- A command must not reimplement a builder. `/wp-yolo` is the model: it normalizes the demo once,
  then drives the existing commands/agents in dependency order.
- Every agent's first mandatory step is to read the **project's** `.claude/CLAUDE.md` (generated by
  `/wp-init` in the user's WordPress project — a different file from this one) to pick up the
  function prefix, languages and theme slug. `prefix_` in agent/skill docs is a placeholder.
- Plugin-relative paths in commands are always `${CLAUDE_PLUGIN_ROOT}/…`, never relative.
- The `.wp-create.json` manifest in a user project is the shared source of truth for the WP-CLI
  wrapper, environment type and language config — commands read it instead of re-asking.

### Recorded decisions — read them, never re-derive them

**i18n strategy.** Two independent systems; do not mix them. `wp-bilingual`: one page, ACF
field `_<lang>` suffixes resolved by `prefix_get_field()`. `wp-polylang`: one post per language
(**the default**). `/wp-init` Step 0.7 writes `i18n strategy` into the project's
`.claude/CLAUDE.md`; `/wp-seed`, `/wp-header`, `wp-acf` and `/wp-yolo` branch on it. When the
line is absent, the project predates the choice and is `suffix`. The seam is `inc/i18n.php`:
templates never call `get_field()` directly.

**Demo mode.** `/wp-demo` and `/wp-yolo` write `demo mode` (craft or plain) into
`.wp-create.json`; `/wp-init`, `/wp-section` and `/wp-finalize` branch on it. Absent means
`plain`. Craft mode needs a browser: `/wp-demo` probes with `bin/demo-verify.mjs --probe`, stops
on exit 2, and never falls back to plain. Craft hands its tokens to `/wp-init` in
`demo/DESIGN.md`.

### A store is a recorded decision

The `store` block of `.wp-create.json` records what a WooCommerce store sells; `/wp-woo-setup`
applies it and `/wp-audit` reads `store.tier`. A value that no longer matches its recorded hash
is the client's and is left alone unless `force` is passed — except launch state, which `force` never writes on a store that already has orders.

Reasoning and history for all three (why Polylang is the default, the craft build and token
aliases, what `plugins/store-kit/` owns): `docs/architecture.md`.

## Authoring conventions

**Command** (`commands/<name>.md`) — frontmatter with `description`, `allowed-tools`,
`argument-hint`. Add `Agent` to `allowed-tools` only if it dispatches subagents.
A command is read whole on every run, so a long step keeps its heading and entry condition in
the command and moves its detail to `skills/<command>-run/references/<step>.md`, read at that
step (`/wp-audit` with `wp-audit-run` is the model; every `skills/*-run/` follows it). Not a
`commands/` subfolder: those load as extra slash commands. Checks read such a command through
`tests/checks/lib/expand-command.sh`, which splices in only the command's own `<command>-run`
references.

**Agent** (`agents/<name>.md`) — frontmatter `name`, `description`, `tools`, `model` (`opus`|`sonnet`|`haiku` — cost tier, see `tests/checks/model-routing.sh`) (order:
`Read, Write, Edit, Grep, Glob, Bash`). Must open with the "First Action (MANDATORY)" block,
and return `BLOCKED: <reason>` plus the files it touched when it cannot proceed, never a guess
(contract and exceptions: `skills/wp-contributing/SKILL.md` § Agent contracts).

**Skill** (`skills/<name>/SKILL.md`) — frontmatter `name`, `description`, `user-invocable: false`.
Skills inform; they never act. The description says what the skill does and ends with a
"Use when …" clause. Keep the body under 500 lines and put templates, long samples and catalogs
in `references/` (`tests/checks/skill-authoring.sh`).

**Starter theme edits** — use the placeholder tokens (`__starter__`, `__STARTER__`,
`__STARTER_NAME__`), replaced by `/wp-init`.

**New behavior needs a check.** A grep-for-required-tokens script under `tests/checks/` that
fails if the contract wording disappears. Under `set -o pipefail` never end a pipe in `grep -q`
or `head` (SIGPIPE makes the check flaky): use `grep >/dev/null -c` and `sed -n 1p`
(`tests/checks/no-early-exit-pipes.sh`). Source `tests/lib/assert.sh` (`fail`, `skip`,
`require_tool`, `need_token`) and commit with mode 100755 (`tests/checks/assert-lib-adoption.sh`).

## Generated-theme conventions (what the agents must emit)

- Fields: `<section>_<element>` / repeaters `<section>_<plural>` / keys `field_<section>_<element>`,
  `group_<section>`; bilingual duplicates append `_<lang>`.
- Templates: always `prefix_get_field()` (never raw `get_field()`), `?:` fallbacks, everything
  escaped (`esc_html`, `esc_url`, `esc_attr`).
- CSS: custom properties for all tokens, BEM, mobile-first `min-width` queries, section delimiters
  `/* ====== Section: Hero ====== */`. In transcription mode (`--transcribe`, `/wp-yolo`) agents copy
  the demo's exact declared values, and scope every selector under a unique BEM block.
- Prefer WP-CLI over generating PHP (`wp-cli-patterns` skill).

## Release chores

Never edit `CHANGELOG.md` in a PR: add a `changes/<slug>.<section>.md` fragment (format in
`changes/README.md`). Update `README.md` when adding a command. A release is a `release/X.Y.Z`
branch and PR, then an annotated tag and `gh release create`; it bumps four version strings and
reconciles `BACKLOG.md` (a gate). Steps: `docs/releasing.md`.

## Known ceilings

Deliberate, documented limits — not bugs to fix on sight. Before "fixing" something in clone,
seed, yolo resume, i18n, craft, image generation, audit, research, store, or the manifest
validator (which binds the commands that call it), read its entry in `docs/known-ceilings.md`.
