# /wp-create — Step 4.2

`commands/wp-create.md` sends the run here at Step 4.2 (Download WordPress) when the user chose **Overwrite** on an existing manifest. Follow it in order; nothing in it is optional background.

Overwrite is a full install, never Adopt Mode, even though `wp-config.php` is still on disk. Read the environment, the database settings (`database.*`), the wrapper (`wp_cli.wrapper`, the `$WP` of this run), the slug (`project.slug`) and the database name (`database.name`) from the existing `.wp-create.json`: the Overwrite choice is made at Step 2b, before Steps 3 and 4 have produced them. Step 3 then reuses the manifest's `database.*` and environment without asking and without generating a new password, so `db reset` (4.4, which reads the old `wp-config.php`) and `config create` (4.5) hit the same database.

1. **Services.** For a container environment (`environment.engine` is `docker-compose`, `ddev`, `lando` or `wp-env`) whose services are stopped, start them with that environment's Step 4.8 command; if that fails, stop and tell the user the backup could not be taken.
2. **Same database.** `db export` and `db reset` read the database from the `wp-config.php` on disk, not from the manifest. Read it with `$WP config get DB_NAME` and compare it with `database.name`. If `config get` fails or prints nothing, stop: the reset would act on a database nobody verified. If they differ, stop and name both: the backup, the confirmation and the reset must all be about one database, and drift between the two files is the user's to resolve.
3. **Export, to the host.** Write the dump outside the WordPress root, with the file on the host and not inside a container. The dump holds password hashes and personal data, so the directory and the file are private to the user (`umask 077`):
   ```bash
   TS=$(date -u +%Y%m%dT%H%M%SZ)
   (umask 077; mkdir -p ~/wp-create-backups && chmod 700 ~/wp-create-backups)
   WP='<wrapper>' bash -c 'umask 077; $WP db export - > "$1"' _ ~/wp-create-backups/<slug>-$TS.sql
   ```
   Also copy, with the same `$TS`, each environment file Step 4.3 will rewrite that exists today (`docker-compose.yml`, `docker/nginx.conf`, `.ddev/config.yaml`, `.lando.yml`, `.wp-env.json`): ports, volumes and extra services in it are the user's, it can hold database credentials, and 4.3 replaces it whole. Keep the copies private and name them by path, so `.ddev/config.yaml` cannot collide with another `config.yaml`: `(umask 077; cp -p .ddev/config.yaml ~/wp-create-backups/<slug>-$TS.ddev-config.yaml)`.
   Copy `wp-config.php` the same way, because step 6 recreates it from the stock template: its own `define()` lines (table prefix, `WP_HOME`/`WP_SITEURL`, cache, debug, Stripe keys read by `store-kit`, salts) exist nowhere else. It holds credentials, so it stays private too: `(umask 077; cp -p "${PROJECT_PATH}/wp-config.php" ~/wp-create-backups/<slug>-$TS.wp-config.php)`. If the copy fails, stop.
   Do not wrap it in `bin/wp-quiet.sh`: that filter rewrites stdout, which here is the dump itself. Require exit 0 and a last non-empty line containing `-- Dump completed`; otherwise delete the file and stop. If WP-CLI reports `Unknown database`, there is nothing to lose: ask whether to continue without a copy. Any other failure: stop.
4. **Confirm.** Ask the user to confirm, naming only what this environment will really replace: the WordPress core files in `${PROJECT_PATH}` (`wp-admin`, `wp-includes` and the root files; `wp-content` is kept), `wp-config.php` (recreated with `config create --force`) and the contents of database `<DB_NAME read in step 2>` (emptied, not the container or server), plus the regenerated environment config (Step 4.3) and the backup paths (dump, `wp-config.php` copy and copied environment files). Without an explicit yes, stop: no 4.2, no 4.4.
5. **Replace.** Step 4.2 runs with `core download --force --skip-content` (the flag is what keeps `wp-content`). Step 4.4 does not run `db create`, which fails on a database that exists: run `$WP db reset --yes` instead (it drops and recreates the database), in every environment. If the database was missing (`Unknown database`), 4.4 runs as written.
6. Step 4.5 runs `config create --force`: without it the run aborts on the existing `wp-config.php` after core and database are already replaced.
7. Back up the old manifest to `.wp-create.json.bak` and continue as if it did not exist.
